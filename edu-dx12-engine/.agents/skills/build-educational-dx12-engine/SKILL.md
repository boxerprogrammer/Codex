# 教育用DX12エンジン開発・教材化

## 判断の軸

**理解しやすさ・可読性 → 拡張性 → 教材転用 → 機能・速度**を守る。学生はC++基礎を既習、DX12・メモリ配置・大きな設計は初学者とする。

## 入口

1. 作業先の`AGENTS.md`と、存在する場合は`docs/PROJECT.md`・`docs/STATUS.md`を読む。ファイルの存在を確認し、ない文書・エンジン・検証をあるものとして扱わない。
2. 明示されたモードを優先し、なければ依頼から[開発モード]または[教材執筆モード]を判断して短く宣言する。
3. 意図が不明な初回だけ役割を名乗り、モードと着手段階を尋ねる。明確な依頼には、その対象を確認文として述べて着手する。準備文書だけの依頼で実装を始めない。
4. 依頼範囲と実装・検証の現在地を合わせ、最小の成果を決める。関連する文書だけを追加で読む。

## 共通の実装基準

- C++20を守る。通常の所有は値または`unique_ptr`、共有するCPU資産は`shared_ptr`、COMは`ComPtr`。API固有の破棄は専用RAIIにする。
- Nodeは子を単一所有し、親は非所有。長期外部参照は失効を検出できるhandleにする。Resource共有とSceneの実行中状態を分ける。
- GPU完了とCPUオブジェクトの寿命を区別し、fence完了前にallocator・upload・descriptor・GPU資源を再利用しない。
- 初期RenderGraphは単一queue、read/write、明示順と状態遷移から始める。大規模RHI・ECS・自動反射・高度な最適化を先に作らない。
- PBRとUnlitの対応段階を明示する。直接光だけのPBRにIBLまで実装済みと書かない。
- 依存ライブラリは採用する版の公式ヘッダ・サンプルを確認する。API署名・互換性・利用条件を推測で埋めない。

- 初出用語に一言の言い換えを付け、具体的な構造・コードへ結びつける。

- Windowsビルド・DX12描画を実施した事実と、Linux等での静的確認を分ける。未実施のテストを成功扱いにしない。
- 作業結果、検証、未実施、次の一手を報告し、既存の進捗文書を更新する。
- 開発は「結論・全体像／選択肢／実装と理由／検証・次の段階」、教材は「目標／動機・図／段階的実装／ミス・デバッグ／演習」を基本形とする。
