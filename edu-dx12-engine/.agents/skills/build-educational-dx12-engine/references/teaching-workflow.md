# 教材手順

## 1. 学習対象の実体を確認する

対象段階、実ファイル・シンボル、依存版、検証記録、学生の前提を確認する。実装がまだ存在しない場合は構成案または設計用の疑似コードと明示し、完成コード由来の教材として扱わない。

## 2. 一回の到達点を決める

90分×2コマを一つの目安にし、学生が説明できることと操作できることを分けて定義する。全DX12初期化やPBR理論を一度に覚えさせず、動く最小の変化へ分割する。

## 3. 学生用本文を書く

1. 学習目標：具体的な行動で3〜5項目を書く。
2. 動機：なぜ必要か、一言の比喩、実際の仕組みへの対応を示す。
3. 図解：所有、時間順、データの流れを別の小さなMermaid図で示す。
4. 実装：実ファイルからC++20/HLSLを引用し、抜粋と省略を区別する。各段階の変更点と意図を説明する。
5. 確認：成功時に見えるもの、実行手順、実行済み/未実施を示す。
6. ミス：症状、原因候補、観察場所、直し方を結び付ける。
7. 演習：基本の穴埋め・改変、発展の自力実装、理由を説明する問題を作る。

## 4. 講師用解答を分ける

学生用は`lessons/students`、解答・採点・補足は`lessons/teachers`を既定とする。実際のプロジェクトの構成があればそれに合わせる。フォルダ分け自体は閲覧制限にならないので、学生配布物には解答を含めない運用を明記する。

採点は「動く」「理由を説明できる」「条件を変えたときの影響を説明できる」で行う。別解を否定せず、要件・安全性・可読性で評価する。

## 5. 実装との整合を確かめる

ファイル名・API名・引数・図・順序・エラー説明が実コードと一致するか確認する。穴埋めの解答は可能ならbuildし、実施できなければ未実施と書く。

教材の説明のためにエンジンを無断で大改造しない。小さな不具合修正が必要なら根拠と影響を明示して直す。長い教材は章や節へ分け、対象段階とソースの対応を記録する。
