# 開発手順

## 1. 根拠を確認する

現在のファイル・未コミット変更・build設定・依存版・エラーを読む。利用できるOSとGPU確認環境を記録する。教材用の仕様だけがある状態を、完成エンジンがある状態と混同しない。

段階の既定順は、環境 → Win32 → DX12 clear → 三角形 → frame context → Node/Scene/Resource → 3D Unlit → 簡易RenderGraph → PBR → ImGui → Lua → XAudio2 → Effekseer → 総合教材。既存プロジェクトに別の明確な計画があればそれを優先する。

## 2. 範囲を小さく定める

依頼された段階と受入条件を明らかにする。一度に複数段階を依頼されていれば、その範囲を前提確認から順に進める。毎段階で許可を取り直さない。

重要な未決事項は2〜3案を比較し、可読性・拡張・教材の難しさを示す。要件を満たす可逆的な初期値は採用理由を記録して進める。

## 3. 実装する

責務・所有・処理順を短く図や表で示した後、必要な最小クラスを実装する。C++20/HLSLコードに「なぜこの順・寿命か」のコメントを添える。外部APIは固定対象のヘッダ・サンプルと照合する。

DirectX 12では、とくに次を扱う。

- Debug Layerはdevice作成前に有効化する。
- command allocatorをGPU完了前にResetしない。
- back bufferのPRESENT / RENDER_TARGET、copy先の状態遷移を追う。
- shader register / root signature / PSO / format / input layoutを揃える。
- upload・descriptor・GPU resourceをframeのfenceと一緒に管理する。
- 最小化で0になった寸法をresizeへ渡さず、resize時に古いbufferと参照を適切に解放する。
- Node走査中の削除、Scene切替後のLua/UI参照を安全に処理する。

## 4. 関連するリスクを検証する

実際のbuildコマンドとサンプル実行を用い、変更で壊れ得る正常系・異常系を確認する。GPU検証が必要な段階はWindowsで行う。環境がなければ未実施と記録する。

テストは意味のある不変条件を確かめる。たとえばhandle失効、親子循環の拒否、graphの未初期化読出し、fence完了後の再利用。何もしないテストや常に真のチェックを置かない。文章修正で全GPUテストを強制しない。

## 5. 障害は観測から絞る

症状と再現条件を記録し、事実／仮説／確認方法を分ける。Debug Layer、GPU-based validation、PIX、DREDは症状に応じて選ぶ。最小修正後に同じ再現手順で確認する。

## 6. 引き継ぐ

変更内容、コマンド、環境、終了コード、観察結果、未実施、次の一手を残す。実装があっても必要な実行確認がなければ「実装済み・検証待ち」。教材本文を求められていない場合は学習要点・つまずきだけを短く記録する。
