# コード規約

この文書は、本プロジェクトの**設計上の取り決め**。C++全般の唯一の正解を主張するものではない。

## C++20の範囲

- C++20を明示し、コンパイラ拡張への依存を抑える。MSVCでは警告レベルを高め、教材コードを警告のない状態に保つ。外部ライブラリの警告設定は自作コードと分ける。
- 初期はヘッダとcppの構成とし、C++20 modulesの導入は保留する。
- `std::span`は所有しない連続データのビュー、`std::string_view`は所有しない文字列のビューとして使う。呼出後も保持するデータは所有型へコピーする。
- `std::expected`、`std::print`などC++23以降の機能を、C++20の例として使わない。問題を解くためだけの汎用テンプレート基盤を先に作らない。

## 名前・ファイル・依存

| 対象 | 取り決め |
| --- | --- |
| 名前空間 | `edu`、必要な範囲で`edu::render`等 |
| 型 | `PascalCase`：`Scene`, `RenderGraph`, `FrameContext` |
| 関数 | `PascalCase`：`Update`, `CreateTexture`, `WaitForFrame` |
| 変数・引数 | `camelCase`：`deltaSeconds`, `frameIndex` |
| 非公開データ | `camelCase_`：`children_`, `device_` |
| 列挙 | `enum class`、値は`PascalCase` |
| ファイル | 原則、主要型と同じ名前の`.hpp` / `.cpp` |
| 言語 | 識別子は英語、教材・意図を説明するコメントは日本語 |

ヘッダは必要な宣言を自分でincludeする。Windows専用ヘッダは`engine/platform/win32`と`engine/render/d3d12`等の境界に留める。`using namespace`をヘッダの大域へ置かない。相互includeの循環を、何でも入った共通ヘッダで隠さない。

## 所有権

| 対象 | 原則 | 注意 |
| --- | --- | --- |
| 一つの所有者を持つC++オブジェクト | 値、または`std::unique_ptr` | 通常の`new` / `delete`を利用側に露出させない |
| 本当に共有するCPU素材 | `std::shared_ptr<const T>`等 | Nodeの親子へ安易に使わない。編集可能データの共有規約を別に定める |
| その呼出中だけ使う参照 | `T&`, `const T&` | 対象の寿命を契約として明記 |
| null可能な短期非所有参照 | `T*` | 所有しないと明記。長期保存しない |
| Nodeの外部・長期参照 | Scene識別子・slot・generation等を持つ`NodeHandle` | Resolve時に有効性を検証。破棄・Scene切替後を扱う |
| COM資源 | `Microsoft::WRL::ComPtr<T>` | GPU利用中の解放が安全になるとは限らない |
| HANDLE・voice等 | API固有のRAII wrapper | すべてが`Release()`対象ではない |

親が子を所有し、子から親への参照は非所有とする。走査中の削除・reparentは安全な境界に遅延する。スクリプト・UI・登録callbackに残る参照の無効化を設計する。

## エラー処理

- HRESULT失敗をそのまま無視しない。呼出API、数値コード、説明、対象資源・shader名等を記録する。
- 回復不能な初期化失敗は、小さな`ThrowIfFailed`等から例外を投げ、アプリケーション境界でcatchして表示・終了する方式を初期案とする。デストラクタ、Win32 callback、audio callback等のABI境界から例外を漏らさない。
- ファイル未発見、Luaの実行エラー等の予測可能な失敗は、その機能の戻り値と短いエラー情報として処理する。実行時に毎フレーム例外を正常制御へ使わない。
- `assert`は内部不変条件の検出用。外部ファイルやデバイス失敗をassertだけで処理しない。
- 黒画面やサウンド失敗を「何も起きない」挙動で隠さず、どこで停止したかを学生が辿れる診断を出す。

## レンダリング

- resource state、fence値、frame index、descriptorの役割を名前で識別する。`index`や`buffer`だけで何の番号・資源か分からない名前を避ける。
- PSO / root signature / shader register / input layout / render target formatの対応を同じ設計資料から追えるようにする。
- constant bufferのオフセット・サイズ・パディングとHLSL側の配置を明記する。C++の型サイズだけで一致を思い込まない。
- `alignas(256)`を付けるだけで全問題が解決したとしない。CBVのサイズ・GPU仮想アドレス配置・upload allocator・フレーム寿命を確認する。
- shaderは独立した`.hlsl` / `.hlsli`に分け、CPUと同じくレビューする。省略コードと実際のコンパイル対象を混在させない。
- 通常Z、LH、行ベクトル等の標準は[RENDERING.md](RENDERING.md)を正本とする。変換を複数箇所へ分散させない。

## 分割の粒度

1クラスは一つの説明可能な責務を持つ。「ウィンドウを管理する」「GPUへ命令を送る」「Nodeを所有する」等、学生が一文で説明できる単位を目安にする。行数だけで機械的に分割せず、目的のない一行wrapperを量産しない。

抽象interfaceは差し替え要求やテスト上の必要が現れたときに追加する。初期から`IManagerFactoryService`のような間接層を作らない。描画APIを隠すことより、責務と寿命を分けることを優先する。

## コメントと教材

良いコメントは「このframeのGPU利用が終わるまでallocatorをResetできない」等、コードから読み取りづらい理由を説明する。構文を日本語へ逐語訳するだけのコメントを増やさない。

教材のC++コードは実ファイルから引用し、相対パス・型/関数名・段階IDを記す。完全なファイル、抜粋、穴埋め、疑似コードのどれかを明示する。抜粋に必要なincludeや文脈を補うが、長い定型コードで学習点を埋めない。

## 変更時チェック

- 新しい概念は、この段階で必要か。
- 各データを誰が所有し、いつ破棄するか説明できるか。
- API境界を越える参照・例外・callbackの寿命は明確か。
- 変更した動作に対応する意味のある確認をしたか。
- 実コード・説明・図・課題の名前や順序が一致しているか。
